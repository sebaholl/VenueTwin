# Owner approval in Studio

Pilot is an opt-in, operator-triggered assistant. In Studio's Project step, the operator saves evidence, reviews extracted findings, writes a brief, and selects **Generate proposal**. A proposal lists its actions, source basis, questions, limits, seat-count effect, and layout checks before any venue edit.

Proposals with actions become pending owner approvals on that browser and project. Refreshing the page restores a pending proposal only when the current venue snapshot and SHA-256 hash of the selected saved evidence still match. Editing the brief, changing source settings, changing materials, or declining clears the proposal. Approval rechecks those inputs immediately before applying the plan. **Approve changes and build** additionally starts the existing local Blender build; a build failure does not roll back the approved layout. The most recent 20 approval/decline decisions are saved locally.

Nothing in this workflow automatically sends an AI request on page load. Each **Generate proposal** click makes one paid API request, or up to two if **Check and attempt one correction** is enabled. Upload analysis and Blender builds retain their existing explicit controls. No approval publishes a viewer or deploys the site.

This is a single-device owner checkpoint, not an authenticated, shared business operations queue. It does not run background jobs, coordinate multiple agents, purchase services, email customers, or certify 1:1 accuracy. A customer release with unattended processing still needs a server-side job queue, owner identity and roles, durable evidence storage, cost budgets and retry limits, approval records, and a publish gate. Geometry and appearance claims require measured seat positions and venue-reviewed comparison views for the exact model revision.

Local verification: `npm test`, `npm run lint`, `npm run build`. To try the owner workflow, use `npm run dev`, open `/studio/workspace`, and select the Project step. `/studio` is a read-only customer demonstration with fictional data. These routes are separated for presentation, not access control; the workspace needs authenticated owner access before a public launch. Pilot requires an explicitly configured local or hosted API; the front page and demo work without it.
